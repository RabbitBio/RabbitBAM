BAM/SAM file manipulation is an essential component of high-throughput sequencing data analysis. 
The continued growth of sequencing datasets increases the computational and I/O demands of these operations, making efficient and scalable processing increasingly challenging. 
Although the Sunway heterogeneous many-core architecture offers substantial computational resources for accelerating BAM/SAM processing, dedicated libraries and applications that exploit this architecture remain lacking.

We present SWBAM, a library and application suite for fast and scalable BAM/SAM manipulation on the Sunway heterogeneous many-core architecture. 
The library provides a set of general-purpose components for BAM/SAM processing, including I/O components for input partitioning and distributed output, as well as four reusable MPE–CPE pipelines for batch-oriented BAM/SAM reading and writing.

\section{Introduction}
%背景 -> 相关工作及局限 -> sunway架构和优势 -> 挑战实现和贡献 √
The rapid growth of high-throughput sequencing data has continuously increased the computational and I/O demands of genomic data analysis~\cite{amarasinghe2020opportunities,goodwin2016coming,schmidt2017ngs}. Following sequence alignment, the resulting data are commonly stored in the SAM (Sequence Alignment/Map) or its binary counterpart BAM (Binary Alignment/Map) format~\cite{li2009samtools}. 
These files undergo a series of processing operations, including statistics, filtering, format conversion, sorting, mate information updating, and duplicate marking, before being used in downstream analyses such as variant calling. 
In typical analysis workflows, large BAM files may therefore be read, reorganized, and rewritten multiple times. 
As sequencing datasets continue to grow, efficient BAM and SAM processing has become increasingly important for maintaining the throughput of large-scale genomic analysis.

SAMtools and HTSlib provide widely used software infrastructure for BAM and SAM processing, supporting operations such as format conversion, sorting, indexing, and duplicate marking~\cite{danecek2021samtools,bonfield2021htslib}. 
Several tools have further improved the performance of specific BAM operations. 
Sambamba employs multithreaded processing for common alignment-file operations~\cite{tarasov2015sambamba}, while quickBAM provides parallel access to sorted and indexed BAM files~\cite{pitman2023quickbam}. 
RabbitBAM focuses on general BAM I/O on multicore CPU platforms and improves parallel efficiency through pre-parsing, parallel parsing, memory pools, and lock-free queues~\cite{yan2025rabbitbam}. These efforts demonstrate the potential of parallel processing for accelerating BAM operations. 
However, existing approaches do not directly address the efficient exploitation of heterogeneous many-core architectures or the coordinated execution of diverse BAM operations across distributed processing units.

The next-generation Sunway platform offers substantial computational resources through its heterogeneous many-core architecture. 
The SW26010-Pro processor consists of multiple Core Groups (CGs), each integrating one Management Processing Element (MPE) and 64 Compute Processing Elements (CPEs). 
The CPEs are organized into an 8 $\times$ 8 array, with each CPE equipped with 256 KB of Local Data Memory (LDM). 
Hardware-supported Direct Memory Access (DMA) facilitates data transfers between the MPE and CPEs, while Remote Memory Access (RMA) enables efficient data exchange among CPEs~\cite{zhu2021sunway}. 
This architecture provides complementary opportunities for parallelism: the CPE array can accelerate computation-intensive operations such as Blocked GNU Zip Format (BGZF) decompression, record parsing, serialization, and compression, while DMA-based data movement supports batch-oriented execution between MPE main memory and CPE local memories. 
Furthermore, multiple CGs can cooperate through MPI, providing a basis for distributed processing of large BAM datasets. 
Previous applications, including SWQC and SWBWA, have demonstrated the effectiveness of redesigning bioinformatics workflows to exploit CPE-level parallelism and MPE-CPE cooperation on this architecture~\cite{yan2025swqc,yan2026swbwa}. 
Nevertheless, efficiently supporting general BAM processing remains challenging because it involves not only data-parallel I/O operations but also application-specific dependencies and coordination across distributed processes.

Efficient BAM processing on Sunway faces three main challenges.
First, conventional BAM libraries expose record-oriented interfaces, whereas fine-grained CPE task dispatch introduces excessive scheduling and synchronization overhead. Efficient execution therefore requires batch-level parallelism and coordinated MPE-CPE execution.
Second, distributed processing requires scalable input partitioning and output organization, enabling MPI ranks to process assigned input regions and collectively produce globally valid outputs without gathering all record payloads on a single rank.
Third, BAM operations exhibit different data dependencies: statistics and filtering are largely batch-independent, whereas sorting requires global ordering, collation and fixmate involve QNAME-based grouping, and duplicate marking requires coordinate-ordered state management across batches and ranks.
These differences make a unified parallelization strategy difficult.
To address these challenges, we develop SWBAM, a high-performance BAM/SAM processing framework for the Sunway many-core platform.
SWBAM provides four batch-based MPE-CPE pipelines for BAM/SAM reading and writing, together with reusable I/O, batch management, scheduling, and output components.
It also provides optimized CPE kernels for BGZF compression and decompression, BAM/SAM parsing and formatting, and record serialization.
A key design principle is to combine pipeline flexibility at batch boundaries with efficient record-level execution: pipelines are composed at the batch level, while performance-critical record operations are statically fused within CPE kernels.
For example, BGZF decompression, BAM parsing, and record-level statistics or filtering can be performed within a single CPE launch, avoiding per-record runtime operator dispatch and unnecessary intermediate processing.
MPE-side batch processing connects these pipelines to support different input-output combinations.
On top of this library, we implement streaming operations, including statistics, filtering, and BAM/SAM conversion, as well as distributed applications for coordinate sorting, collation, fixmate, and duplicate marking.
These applications incorporate operation-specific data redistribution and cross-rank coordination.
In particular, duplicate marking adopts a one-pass coordinate-streaming algorithm with a sliding window, boundary handling, and incremental output.
The distributed applications are further integrated into a complete four-stage deduplication workflow.

The main contributions of this work are as follows:
\begin{itemize}
    \item We design the SWBAM library, a reusable BAM/SAM processing framework for the heterogeneous Sunway many-core architecture, providing four batch-based MPE-CPE pipelines and common processing components.
    \item We develop optimized CPE kernels and a batch-oriented execution model that combines pipeline composition with static fusion of record-level operations, reducing fine-grained scheduling and intermediate processing overhead.
    \item We implement distributed BAM applications, including coordinate sorting, collation, fixmate, and duplicate marking, and integrate them into a complete deduplication workflow. We evaluate the framework at the library, application, and workflow levels on the Sunway platform.
\end{itemize}

\section{Methods}
\subsection{Overview}
% 总体介绍+库的介绍 -> app的介绍 -> overview图 √
As shown in Fig.~\ref{fig:swbam_overview}, SWBAM consists of a library and a set of applications that use its components.
The library provides common BAM/SAM I/O components for input partitioning and distributed output.
It also provides four batch-based pipelines for BAM reading, BAM writing, SAM reading, and SAM writing.
These pipelines use buffer reuse and double buffering to coordinate MPE--CPE execution.
MPE-side batch post-processing connects processing stages, while batch-level operators define task-specific operations.
Where appropriate, record-level operations are combined within CPE kernels.
CPE kernel optimizations further reduce allocation and data movement overhead in BGZF compression and decompression, BAM/SAM parsing and formatting, and record serialization.
These optimizations include codec reuse, reusable record buffers, and fused processing.

SWBAM applications reuse the library's components and implement algorithms for their specific data dependencies.
Streaming applications combine the relevant pipelines and operators for statistics, filtering, and BAM/SAM conversion.
The distributed applications build on the shared BAM read/write pipelines, using operation-specific algorithms and MPI communication to redistribute and reorder records and coordinate state across ranks.
Sorting and collation redistribute records by coordinate and QNAME, respectively.
Fixmate processes QNAME groups across batch and rank boundaries, while duplicate marking maintains a coordinate-ordered candidate window and coordinates duplicate decisions across ranks.
These operations are combined into a four-stage deduplication workflow: collation, fixmate, coordinate sorting, and duplicate marking.

\subsection{SWBAM Library Design}
\subsubsection{BAM/SAM input and output}
%总结+分布式输入 → 分布式输出 √
SWBAM provides reusable BAM/SAM I/O components so that applications do not need to implement data access separately.
Applications can use the same processing pipelines with different I/O methods.
For BAM input, SWBAM divides BGZF blocks into contiguous ranges and assigns each range to an MPI rank.
The root rank scans the data region and builds an ordered index of block offsets and compressed sizes.
It reads compressed data into an 8-MiB buffer and examines successive BGZF headers in memory, reducing small file reads during block-boundary detection.
The root rank then broadcasts the index to all ranks.
The blocks are divided into contiguous ranges with approximately equal block counts.
During processing, each rank reads only its assigned blocks through POSIX or MPI-IO.
Within each contiguous batch, the BGZF blocks are read directly into separate destination buffers for CPE processing.
The POSIX path uses \texttt{preadv} to read a contiguous file region into a list of buffers.
The MPI-IO path uses a derived datatype to place each block in its corresponding destination buffer.
Both paths avoid an intermediate buffer and the subsequent copy of individual blocks.
For SAM input, SWBAM divides the text after the header into approximately equal byte ranges.
It adjusts partition boundaries to line ends so that each record remains intact within a single rank.
Each rank reads its assigned range through POSIX or MPI-IO.

SWBAM writes distributed output in two stages because each rank produces a different amount of data.
Each rank first appends its output body to a local store in memory or a temporary file.
In automatic mode, the store switches to a temporary file when an append would exceed the memory limit.
After processing, ranks exchange body sizes and use prefix sums to calculate file offsets in rank order.
Each offset is determined by the header size and the output sizes of all preceding ranks.
In MPI-IO mode, each rank reads its staged body through a fixed-size buffer and writes it to the assigned file region.
This avoids gathering complete output bodies on the root rank, reducing its memory requirements during final output generation.
The BAM output consists of one header, the rank-local compressed bodies in rank order, and one BGZF EOF block.
The SAM output consists of one text header followed by the rank-local text bodies.
File-backed staging allows SWBAM to handle outputs larger than the available staging memory without keeping the entire output in memory.

\subsubsection{Batch-based MPE-CPE pipelines}
%总结+为什么以batch为核心 -> 介绍4条流水线 -> 介绍双缓冲优化 √
SWBAM provides four batch-based MPE-CPE pipelines for BAM reading, BAM writing, SAM reading, and SAM writing.
Batch-based execution reduces the kernel launch and synchronization overhead associated with per-record processing.
The MPE prepares input batches and manages task execution, while the CPEs perform the corresponding processing kernels.

The BAM read pipeline processes batches of compressed BGZF blocks.
The CPEs decompress the blocks and, when required, parse BAM records or perform application-specific operations.
The BAM write pipeline accepts uncompressed data blocks or batches of BAM records.
The CPEs compress the input blocks directly or serialize the records before compression.
Both pipelines produce or consume batches of BGZF blocks and support rank-local data processing.
The SAM read pipeline converts rank-local SAM text into batches of \texttt{bam1\_t} records.
The MPE divides the text into chunks aligned to record boundaries.
The CPEs first copy the text and count records, then parse the SAM fields in a separate kernel.
The SAM write pipeline converts batches of \texttt{bam1\_t} records into SAM text.
The CPEs format records into separate text buffers, and the MPE appends the results in record order.

SWBAM uses alternating buffers to overlap MPE-side work with CPE execution, as illustrated by the BAM read schedule in Fig.~\ref{fig:swbam_overview}.
For BAM reading, the MPE reads the next compressed batch while the CPEs process the current batch.
For BAM writing, the MPE writes the previous compressed batch while the CPEs compress the current batch.
Similar overlap is used in SAM processing, depending on the pipeline stages and data dependencies.
These strategies reduce idle time and reuse allocated buffers across batches without requiring multiple CPE kernels to execute concurrently within the same core group.

\subsubsection{Pipeline composition and operators}
% 总结+简单解释流水线和operators -> CPE记录级组合 -> 流水线组合以及两个sdk组合示例 -> 介绍数据所有权与生命周期管理 √
SWBAM composes processing at two levels: record-level operations within CPE kernels and batch-level stages through MPE-side post-processing.
This design reuses common pipeline mechanisms while allowing applications to combine different operations without per-record dispatch overhead.
The pipeline runtimes manage batch buffers, launch and join CPE kernels, and invoke MPE-side hooks.
For each batch, an MPE-side operator provides the kernel entry and task-specific parameters, binds data buffers, validates the results, and performs batch-level post-processing.
These operators are invoked once per batch rather than once per record.

Within CPE kernels, SWBAM combines common BAM record traversal with task-specific operations, including record counting, flag statistics, filtering, and passthrough processing.
C++ templates determine the record operation when the kernel is compiled.
At runtime, the MPE selects among prebuilt kernels and passes task-specific options, such as filter parameters.
The record traversal invokes the selected operation directly, avoiding per-record virtual or function-pointer dispatch.

Batch-level composition connects pipelines through MPE-side post-processing after kernel completion and result validation.
For record counting, the BAM read pipeline parses records into reusable \texttt{bam1\_t} objects, and the MPE aggregates the per-block counts.
For BAM-to-BAM processing, the MPE groups retained records into BGZF packing plans and submits them to the BAM write pipeline for serialization and compression.
These plans reference existing records and do not copy record payloads or transfer ownership.

SWBAM also defines data ownership and lifetime across pipeline stages.
Pipeline-owned data remain valid only until their buffers are reused or released.
In BAM-to-BAM processing, parsed records remain in the read operator's storage until the downstream write call finishes consuming them.
The write call completes serialization and compression before returning, although compressed output may remain buffered for later writing.
Applications that retain data across batches manage its lifetime through their operators or algorithm-specific storage, copying data or directing kernel output to longer-lived storage when needed.

\subsubsection{CPE kernel optimizations}
%总结 -> BAM相关优化 -> SAM相关优化 √
SWBAM optimizes CPE kernels to reduce repeated allocation, compression overhead, and intermediate data movement.
It reuses codec objects and working buffers, and combines related processing steps within a single kernel execution.

SWBAM reuses libdeflate compressor and decompressor objects across kernel launches.
The Sunway-adapted implementation of libdeflate allocates these objects in each CPE's local data memory (LDM), thereby reducing main-memory accesses during compression and decompression.
Each CPE creates a decompressor on first use and reuses it for subsequent blocks.
Compressors are cached by compression level and recreated only when the required level changes.
For level-1 compression, SWBAM reduces match-search work by checking one hash-table candidate at each search position.
For sufficiently long matches, hash updates cover the first six interior positions and then use a two-byte stride.
These changes reduce candidate checks and hash-table updates while retaining valid DEFLATE and BGZF output.
This optimization trades compression ratio for throughput, increasing the compressed BAM size by 2.82\% on average (2.50\%--2.99\% across D1--D3) compared with the original level-1 compressor.
For BAM input, SWBAM combines decompression, parsing, and record processing within one CPE kernel.
The decoded block is processed directly without a separate kernel launch or MPE-side processing stage between these operations.
Statistical kernels reuse a scratch \texttt{bam1\_t} record and its data buffer on each CPE.
BAM transform kernels instead store parsed records in preallocated arenas that are reused across batches, reducing per-record allocation.
For BAM output, SWBAM combines record serialization and BGZF compression within one CPE kernel.
Each CPE serializes the records specified by a packing plan into a reusable uncompressed BGZF payload buffer and compresses the payload directly.
This avoids an intermediate payload copy and a separate kernel launch between serialization and compression.
When serialized BAM payloads are provided directly, the kernel skips record serialization and compresses the input bytes.
Compressed output buffers are also reused across batches.

SWBAM also reuses buffers in SAM processing.
The fast SAM parser stores parsed records in per-chunk arenas and caches recent reference-name lookups within each chunk.
For SAM output, each CPE formats records directly into its batch text buffer instead of creating a separate string for each record.
The MPE reserves buffer capacity before formatting and retains enlarged buffers for subsequent batches.
These optimizations reduce repeated allocation and intermediate data handling in SAM parsing and formatting.

\subsection{Applications Built on the SWBAM Library}
\subsubsection{Streaming BAM processing}
%总结+解释流式处理 -> 统计、过滤/重新、格式转换介绍 -> 与分布式算法的区别 √
SWBAM provides streaming BAM/SAM operations for statistics, filtering, rewriting, and format conversion.
These operations process records in input order without global record reordering, allowing each MPI rank to process its assigned input range independently.
For BAM input, record processing follows a separate BGZF scan that builds the block-span index.

Flag statistics use the BAM read pipeline and aggregate results at batch and rank levels.
CPEs update separate counter arrays, and the MPE-side flagstat operator merges these counters into rank-local totals after each batch.
An MPI sum reduction combines the rank-local totals on the root rank to produce the final report.
This operation does not generate an output BAM stream.
BAM filtering and rewriting connect the BAM read and write pipelines through the MPE-side transform operator.
The operator selects the filtering or passthrough CPE kernel according to the requested options.
After each batch, MPE post-processing groups references to retained records into packing plans that satisfy the BGZF payload-size limit.
The BAM write pipeline consumes these plans and appends the resulting compressed blocks to each rank's local output body.
Records retain their input order within each rank, and the final file places rank-local bodies in input-range order without coordinate- or QNAME-based sorting.
Format conversion connects the read pipeline for the input format to the write pipeline for the output format.
For BAM-to-SAM conversion, the MPE-side conversion operator forwards parsed BAM record references to the SAM write pipeline.
For SAM-to-BAM conversion, MPE post-processing builds packing plans from parsed SAM records and submits them to the BAM write pipeline.
Intermediate records remain valid until the downstream pipeline finishes consuming them, allowing the two pipelines to operate on batches without an additional record-level dispatch layer.

These streaming operations require little inter-rank communication after input partitioning because record processing remains local to each rank.
In contrast, the distributed algorithms described next require record redistribution or cross-rank state.

\subsubsection{Distributed BAM processing}
%总结+分布式数据依赖 -> Sorting and collation -> Fixmate -> Duplicate marking √
SWBAM implements distributed BAM operations that require global record reorganization or cross-record state.
Sorting establishes a global coordinate order, whereas collation groups records by QNAME.
Fixmate updates mate information for complete QNAME groups, and duplicate marking compares candidates across batches and MPI rank boundaries.
These applications reuse the common BAM read and write pipelines, while application-specific algorithms manage record redistribution, boundary handling, and cross-rank state.

Sorting establishes a global coordinate order through sampling, redistribution, and merging (Fig.~\ref{fig:swbam-reordering}).
CPEs extract coordinate keys and raw BAM records, while the MPE sorts local metadata and selects samples from the ordered records.
The root rank collects the samples, determines global splitters, and broadcasts them to define coordinate ranges for the MPI ranks.
Records are then exchanged according to these splitters.
Because the received segments are individually ordered, each rank performs a $k$-way merge rather than sorting all received records again.
The merged raw records are packed into BGZF payloads and compressed through the common BAM write pipeline.
Collation uses QNAME-based partitioning instead of constructing a global coordinate order.
CPEs extract QNAME hashes, record metadata, and raw BAM records.
Each hash is assigned to a bin, and each bin is mapped to an owner rank so that records with the same QNAME reach the same rank.
Figure~\ref{fig:swbam-reordering}(b) illustrates six coordinate ranges and 66 QNAME bins mapped to six ranks.
After local ordering, each rank retains self-owned records and exchanges the remaining records in bounded chunks.
The receiving rank merges the segments by bin, hash, and full QNAME, grouping records with the same QNAME together without imposing a global lexicographic QNAME order.
Within each group, records are ordered by READ1/READ2 flag bits and then by original input order.
Unlike the standard temporary-bin workflow of SAMtools~\cite{danecek2021samtools}, SWBAM supports both in-memory and external-memory collation.
Sorting also supports in-memory and external-memory execution.
In external mode, SWBAM generates sorted runs and performs bounded data exchange and streaming multi-way merging under the configured memory limit.
The merge fan-in \(F\) specifies the maximum number of sorted segments merged in each pass. 
If the number of segments exceeds this limit, multiple intermediate merge passes are performed before the final merge and compression (Fig.~\ref{fig:swbam-reordering}(c)).

Fixmate updates mate information for records with the same QNAME.
Because the input BAM is name-collated, records with the same QNAME appear consecutively. 
The MPE scans each batch and groups adjacent records with matching QNAMEs. If a group extends beyond the current batch, it is retained and continued when the next batch is processed. 
A similar situation occurs at MPI rank boundaries, where the last group of one rank may continue as the first group of another. 
Each rank therefore temporarily retains its boundary groups and exchanges their QNAMEs with other ranks to identify fragments belonging to the same group. 
These fragments are then transferred to the designated owner rank for group completion.
Once all records sharing a QNAME have been gathered, a first CPE kernel determines the mate-related field and tag updates for each record and computes its resulting length.
Since tag updates may change record lengths, the MPE uses these lengths to assign non-overlapping regions in the output buffer.
A second CPE kernel then applies the updates and writes the updated records to their assigned regions.
The supported updates include mate coordinates, flags, template length, and the \texttt{MQ}, \texttt{MC}, and \texttt{ms} tags.
The rewritten records are then serialized and compressed through the common BAM write pipeline.
Boundary and interior output segments are combined in QNAME-group order.

%输入处理 -> 通信来源和实现 -> 滑动窗口机制 -> 输出处理
Duplicate marking is implemented as a coordinate-ordered streaming algorithm with a bounded boundary prepass, while preserving the original input order. 
The coordinate-sorted BAM file is partitioned into contiguous BGZF-block ranges, each assigned to an MPI rank. 
For each batch, the shared BAM read pipeline decompresses and parses the input blocks, and a CPE kernel extracts the duplicate key and quality-based score of each candidate.
Single-end keys identify the reference, unclipped $5'$ coordinate, and strand, whereas paired-end keys include both reference coordinates, orientation-dependent unclipped endpoints, and pair orientation. 
The MC and ms tags generated by the preceding fixmate operation provide the mate CIGAR and score required for paired-end processing, avoiding the need to retrieve mate records.

Since duplicate-key coordinates may differ from the alignment-start coordinates used for input partitioning, candidates sharing the same key may originate from different source ranks. 
The MPE routes each candidate to an owner rank determined by the reference and coordinate of its local (this) end. 
For paired-end candidates, both endpoints are retained in the duplicate key, while the local-end coordinate determines ownership. 
This deterministic mapping guarantees that candidates with identical duplicate keys are assigned to the same owner rank. Candidates are processed locally when the owner is the source rank; otherwise, only their metadata is exchanged. 
Each owner maintains separate candidate states for paired-end and single-end reads, including pair-presence information for handling interactions between the two types.
Candidates sharing a duplicate key are compared by quality-based scores, with QNAME used for tie-breaking. 
Decisions are then applied locally or returned to the source ranks through MPI, while the original BAM records remain on their source ranks. 
To reduce cross-rank coordination during the main scan, SWBAM performs a bounded prepass over partition boundaries. Each rank probes up to 32 BGZF blocks at both ends of its input range, processing overlapping blocks only once. 
This limit bounds the prepass workload but does not guarantee complete coverage. 
For a boundary at coordinate $b$, the prepass selects candidates whose alignment starts fall within $[b-L,b+L]$ on the same reference and compares them on their respective owner ranks. 
The resulting boundary plan associates decisions with their source-record identifiers. When the probes cover all required candidate regions, both KEEP and DUP decisions can be finalized. 
Otherwise, only DUP decisions established by the observed competing candidates are finalized, while potential winners remain unresolved for the main pass. 
This conservative treatment prevents premature KEEP decisions before all relevant candidates have been considered.

During the main pass, each owner maintains a sliding window of unresolved candidate keys, using reusable hash-table storage and QNAME buffers across batches. 
Incoming candidates are compared with current winners, and a candidate that outranks the current winner replaces it, marking the previous winner as DUP. 
For an interior key whose remaining comparisons are confined to the local rank, the winning record can be finalized as KEEP when
\[
x+L\leq p_r,
\]
where $x$ is the local-end coordinate of the duplicate key on the current reference and $p_r$ is the latest alignment-start coordinate processed by rank $r$. 
Under the configured bound $L$, this condition ensures that no subsequently processed alignment can contribute to the same duplicate key. 
The bound is specified through the command-line option -l, following the maximum expected read-length convention of SAMtools. 
We use the SAMtools default of 300 bp ($L=300$ bp) in all experiments. 
In SWBAM, $L$ also determines the candidate-retention range and boundary-tracking extent, but does not affect duplicate-key construction or equality. 
As in SAMtools, the bounded-window mechanism relies on an appropriate expected read-length setting. 
Candidates that may still require cross-rank comparisons are retained in persistent boundary tables until all potentially contributing ranks have processed coordinates beyond the corresponding release threshold, advanced to a later reference, or reached EOF. 
Ranks exchange processing progress and EOF status through collective communication when boundary tracking is required. 
Ranks that exhaust their input continue participating with empty batches, and current-round candidates are processed before boundary states are released.

The original decoded blocks remain on their source ranks, avoiding the redistribution of complete BAM records and an additional full-file decoding pass. 
Records are initially assigned provisional KEEP states, while unresolved candidates and records awaiting remote decisions are marked as pending. 
A block is compressed only after all its record decisions have been resolved. 
Since compression may complete out of order, SWBAM tracks each compressed fragment by its input-block index and fragment position, then assembles the fragments in the original input order. 
Decoded buffers are retained until their compression tasks complete, with unresolved blocks staged temporarily under buffer pressure. 
To overlap candidate management with CPE compression, SWBAM launches a prepared compression batch after decoding the next input batch. 
The shared BAM write pipeline handles compression and output generation, while the duplicate-marking application manages candidate states, boundary information, MPI decisions, pending blocks, and output ordering.
Algorithm~\ref{alg:distributed_markdup} summarizes the procedure.

\begin{algorithm}[!t]
\caption{Distributed duplicate marking on rank $r$}
\label{alg:distributed_markdup}
\small
\hspace*{\algorithmicindent}\textbf{Input:}

\hspace*{\algorithmicindent}\textbf{Output:}

and output $O_r$

\State $T \gets \lceil N_{\max}/64 \rceil$
\For{$t=1,\ldots,T$}
    \State $(B_r,C_r,p_r) \gets
    \Call{DecodeAndExtractOrEmpty}{t}$
    \Comment{$B_r$: decoded blocks; $C_r$: candidate metadata; $p_r$: latest processed alignment-start coordinate}
    \State \Call{StartPreparedCompression}{}
    \Comment{Overlap CPE compression with MPE-side candidate processing}
    \State \Call{RetainBatch}{$B_r,Q_r$}
    \Comment{Initialize provisional record states}
    \State \Call{ApplyBoundaryPlan}{$C_r,H_r,Q_r$}
    \If{\Call{NeedsBoundaryTracking}{$H_r$}}
        \State $S \gets
        \Call{AllGatherProgress}{p_r,\text{batch status}}$
    \EndIf

\subsubsection{Deduplication workflow}
%总结+解释四个阶段的执行顺序+介绍中间文件与参数管理 √
SWBAM combines collation, fixmate, coordinate sorting, and duplicate marking into an end-to-end deduplication workflow.
The stages run in this order because fixmate requires records with the same QNAME to be grouped together, while duplicate marking requires updated mate information and coordinate-sorted input.
The workflow first groups records by QNAME using collation, then runs fixmate with mate-score calculation enabled, sorts the updated records by genomic coordinate, and finally marks duplicates.
Each stage uses the corresponding distributed SWBAM application and the common BAM input and output interfaces.
The output of each stage is written to an intermediate BAM file and passed to the next stage.
The workflow produces collated, fixmate-updated, and coordinate-sorted intermediate files before generating the final duplicate-marked BAM file.
Intermediate files can be removed automatically after use or retained for debugging and validation.
The memory limit and compression settings are propagated to the relevant stages, while sorting and collation can use their external-memory implementations when needed.

\subsection{Performance of the SWBAM Library}
%测试说明 → SWBAM扩展性分析 → 三种库的性能分析
We evaluate the scalability of SWBAM's BAM I/O library using two benchmarks: read-only record counting and unfiltered read-and-write. 
The read-only benchmark decompresses BGZF blocks, parses BAM records into reusable \texttt{bam1\_t} objects, and counts them. 
The read-and-write benchmark additionally packs, serializes, and compresses all records before writing a complete BAM file. 
Figure~\ref{fig:library-io} reports throughput for both the end-to-end interval, including MPI initialization and finalization, and the processing interval, excluding these phases.
SWBAM achieves near-linear processing-phase scaling from one to twelve active CGs, with speedups of 10.77--10.90$\times$ for read-only processing and 11.54--11.58$\times$ for read-and-write processing, corresponding to approximately 90\% and 96\% parallel efficiency, respectively. 
This scalability is achieved by distributing contiguous BGZF input ranges across MPI ranks and exploiting block-level parallelism within each CG, while double buffering overlaps MPE-side data movement with CPE execution. 
Although read-and-write processing introduces additional packing, serialization, compression, and output assembly, these operations remain largely rank-local. 
In particular, final output assembly exchanges output sizes rather than record payloads, avoiding inter-rank record redistribution. 
MPI initialization and finalization, however, introduce an approximately 7-s overhead per invocation, substantially reducing end-to-end scaling for shorter workloads. 
Consequently, the one-to-twelve-CG speedups decrease to 2.55--4.43$\times$ for read-only processing and 5.13--7.99$\times$ for read-and-write processing, corresponding to end-to-end parallel efficiencies of approximately 21\%--37\% and 43\%--67\%, respectively. 
This overhead is particularly evident in short read-only executions: for example, D1 requires only 1.38~s for processing at twelve CGs, compared with 8.53~s for the full MPI interval. 
Longer read-and-write workloads amortize the fixed MPI overhead more effectively, highlighting the distinction between the scalability of BAM processing and the additional cost of MPI startup and shutdown.

We further compare SWBAM with SAMtools and RabbitBAM at six active CGs (Table~\ref{tab:library-io-comparison}).
Based on processing time, SWBAM achieves speedups of 3.82--4.35$\times$ and 2.77--3.41$\times$ over SAMtools for read-only and read-and-write processing, respectively, and 2.44--3.34$\times$ and 1.72--3.26$\times$ over RabbitBAM.
These gains result from distributing record processing across MPI ranks and CPEs. 
Unlike SAMtools, which retains record traversal on its main thread, SWBAM performs decompression and record parsing on CPEs. 
Compared with RabbitBAM, SWBAM avoids intermediate record-block assembly during reading and integrates serialization and compression within the same CPE kernel during writing, reducing intermediate data handling and scheduling overhead. 
When MPI initialization and finalization are included, the speedups over SAMtools decrease to 1.12--1.93$\times$ and 1.77--2.19$\times$, respectively, while those over RabbitBAM are 0.64--1.24$\times$ and 1.16--1.82$\times$. 
RabbitBAM remains faster on D1 and D3 for read-only processing, whereas SWBAM retains an advantage for read-and-write processing across all three datasets, highlighting the impact of MPI startup and shutdown on shorter workloads.

Flag statistics achieves speedups of 1.03--1.82$\times$, benefiting from parallel BGZF decoding, record parsing, and flag accumulation on CPEs, whereas SAMtools retains record traversal and counter updates on its main thread. 
MAPQ filtering achieves speedups of 1.57--2.22$\times$ because, unlike flag statistics, it requires retained records to undergo serialization and BGZF compression.

Although both implementations parallelize BGZF compression, SWBAM additionally performs record packing and final output assembly. 
BAM-to-SAM achieves the highest speedups, ranging from 3.17$\times$ to 4.61$\times$. 
This advantage stems from distributing the complete record-processing path across six ranks, with CPEs performing record construction and parallel SAM formatting through batch-level record-pointer handoff. 
SAMtools also parallelizes SAM formatting, but retains main-thread record traversal and submission to an ordered output dispatcher. 
The resulting advantage therefore reflects differences in the organization of the complete conversion pipeline rather than formatting parallelism alone. 
SAM-to-BAM achieves speedups of 1.96$\times$, 2.95$\times$, and 2.26$\times$ on D1, D2, and D3, respectively. 
Both implementations parallelize SAM parsing and BGZF compression. 
SWBAM distributes parsing and compression across rank-local CPE pipelines, whereas SAMtools uses a shared worker pool but retains main-thread record submission and BAM serialization.

\subsubsection{Distributed BAM processing}
Despite an additional overhead of approximately 7~s for MPI initialization and finalization, SWBAM achieves speedups of 1.33--3.32$\times$ across the four distributed operations. 
Coordinate sorting benefits most consistently, whereas duplicate marking exhibits the strongest dataset dependence. 
These differences reflect the varying degrees of parallelism exposed by each operation and the costs of maintaining operation-specific state across batches and ranks.

Coordinate sorting achieves speedups of 2.85--3.32$\times$. 
Although SAMtools parallelizes radix sorting and BGZF I/O, its main thread still loads records into a shared memory arena and drives the final heap merge. 
SWBAM distributes record extraction, local ordering, coordinate partitioning, and range-local merging across six ranks, while CPEs handle BGZF block processing. 
It also sorts compact coordinate metadata while retaining the original BAM payloads, avoiding the construction of a separate \texttt{bam1\_t} object for every stored record. Thus, its advantage comes from distributing more of the end-to-end reordering pipeline and reducing record representation overhead, rather than from a faster local sorting algorithm.
Collation achieves speedups of 2.42--2.67$\times$. 
SAMtools writes records into compressed temporary bins and subsequently reads and sorts these bins on the main thread. 
SWBAM distributes hash bins across ranks, while QNAME comparisons and payload packing remain MPE-side operations. 
For collation on D1 and D3, SWBAM uses its in-memory collation implementation, avoiding the temporary-file writes and subsequent reads required by SAMtools. 
On D2, external-run processing achieves speedups of 2.67$\times$ for collation and 3.32$\times$ for coordinate sorting, despite the additional intermediate writes and merging.
Fixmate achieves relatively stable speedups of 1.67--1.93$\times$. 
SAMtools performs QNAME grouping and mate-field updates on the main thread, with worker threads primarily handling BGZF I/O. 
SWBAM offloads mate-update planning and record rewriting to CPEs, but QNAME group scanning and output-offset construction remain on each MPE. 
These remaining MPE-side operations, together with output serialization and compression, limit the benefit of offloading mate updates.
Duplicate marking achieves speedups of 2.61$\times$, 2.19$\times$, and 1.33$\times$ on D1, D2, and D3, respectively. 
Although CPEs accelerate BGZF decoding, candidate extraction, and compression, candidate-state maintenance and cross-rank coordination remain primarily MPE-side tasks.
The resulting candidate-state maintenance overhead depends on the number of unresolved candidates and how long their states must be maintained. 
On D1 and D2, the boundary prepass covers the required regions, avoiding candidate payload exchanges during the main scan. 
However, the larger unresolved state and greater rank-local workload imbalance on D2 increase state-management costs and delay collective progress. 
D3 incurs additional overhead because partial boundary coverage requires continued boundary tracking and cross-rank candidate coordination. 
Together with the buffering required for unresolved blocks and ordered output generation, these factors explain the dataset-dependent performance. 
Overall, duplicate-marking efficiency depends not only on input size but also on candidate-state management, boundary coordination, and rank-local workload balance.

\section{Conclusions}
This work presents SWBAM, a library and application suite for fast and scalable BAM/SAM file manipulation on the Sunway heterogeneous many-core architecture. 
SWBAM combines reusable batch-based MPE-CPE pipelines with optimized CPE kernels to support efficient BAM/SAM I/O and record processing, and provides a range of rank-local and distributed operations integrated into a complete four-stage deduplication workflow.
Experimental results demonstrate 90\%--96\% processing-phase parallel efficiency when scaling the library from one to twelve CGs. 
Although MPI initialization and finalization introduce approximately 7~s of overhead per invocation, SWBAM achieves speedups of 1.03--4.61$\times$ for streaming operations, 1.33--3.32$\times$ for distributed operations, and 2.27--2.70$\times$ for the complete deduplication workflow over SAMtools, including MPI overhead. 
These results demonstrate the effectiveness of heterogeneous many-core execution for accelerating diverse BAM/SAM operations. 
Future work will focus on improving duplicate-marking performance under irregular coordinate distributions and reducing MPI overhead for short-running workloads.
