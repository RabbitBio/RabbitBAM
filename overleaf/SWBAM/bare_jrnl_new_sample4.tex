\section{Introduction}
The rapid growth of sequencing data continues to increase the computational and storage requirements of genomic data analysis~\cite{amarasinghe2020opportunities,goodwin2016coming,schmidt2017ngs}.After sequence alignment, results are commonly stored in the SAM (Sequence Alignment/Map) or BAM (Binary Alignment/Map) format~\cite{li2009samtools}.These files are subsequently processed by a series of operations, including statistics, filtering, format conversion, sorting, mate information updating, and duplicate marking, before being used by downstream analyses such as variant calling.Many analysis workflows therefore read, reorganize, and rewrite large BAM files multiple times.As sequencing datasets continue to grow, efficient BAM and SAM processing becomes increasingly important for the overall throughput of large-scale genomic analysis.

SAMtools and HTSlib provide the widely used software infrastructure for BAM and SAM processing and support operations such as format conversion, sorting, indexing, and duplicate marking~\cite{danecek2021samtools,bonfield2021htslib}.Several tools have further improved the performance of specific BAM operations.Sambamba uses multi-threaded processing for common alignment-file operations~\cite{tarasov2015sambamba}, while quickBAM provides parallel access to sorted and indexed BAM files~\cite{pitman2023quickbam}.Our previous work, RabbitBAM, focuses on general BAM I/O on multi-core CPU platforms and improves parallel efficiency through pre-parsing, parallel parsing, memory pools, and lock-free queues~\cite{yan2025rabbitbam}.These approaches demonstrate that BAM processing can benefit substantially from architecture-aware optimization.However, their parallel models are mainly designed around conventional CPU threads and do not directly address heterogeneous many-core execution and distributed BAM processing.

The new Sunway architecture provides strong computing capability but also introduces a different execution model.The SW26010-Pro processor consists of multiple Core Groups (CGs), each containing one Management Processing Element (MPE) and 64 Compute Processing Elements (CPEs), while MPI is typically used for communication among processes on different CGs~\cite{zhu2021sunway}.Previous work such as SWQC and SWBWA has shown that bioinformatics applications can achieve high performance on this architecture by moving computation-intensive operations to CPEs and redesigning the original parallel workflow for MPE-CPE execution~\cite{yan2025swqc,yan2026swbwa}.However, BAM processing introduces additional challenges because it combines compressed file I/O, record parsing, format conversion, and application-specific data dependencies.

Efficient BAM processing on Sunway faces three main challenges.First, BAM and SAM libraries naturally expose record-oriented operations, whereas launching and synchronizing CPE tasks for individual records would introduce excessive fine-grained overhead. An efficient design therefore requires both a coarser execution unit and a suitable division of work between the MPE and CPEs. The processing workflow must coordinate MPE-side data preparation and post-processing with CPE computation to reduce synchronization overhead and idle time.Second, distributed BAM processing requires scalable data access and output organization.Multiple MPI ranks should directly process their assigned input regions and generate a valid global output without relying on a single rank to distribute or collect the complete file.Third, BAM applications have very different data dependencies.Simple operations such as statistics and filtering can be performed independently on individual batches, whereas sorting requires global data redistribution, fixmate requires QNAME-based grouping, and duplicate marking requires coordinate-ordered cross-record and cross-rank state.

To address these challenges, we develop SWBAM, a high-performance BAM and SAM processing library and application framework for the Sunway many-core platform.At the library level, SWBAM provides four batch-based MPE-CPE pipelines for BAM reading, BAM writing, SAM reading, and SAM writing.The library separates storage access from computation and supports reusable I/O, batch management, CPE scheduling, and output components.Different processing operators can be attached to these pipelines according to the required operation.SWBAM also optimizes the major CPE kernels for BGZF compression and decompression, BAM parsing, SAM parsing and formatting, and record serialization.At the application level, these common components are reused to implement both streaming operations and distributed BAM algorithms, including statistics, filtering, BAM/SAM conversion, sorting, collation, fixmate, and duplicate marking.The distributed applications further manage global data redistribution, cross-rank communication, and algorithm-specific state.

A key design principle of SWBAM is to provide flexibility at batch boundaries while keeping record-level processing efficient.Pipeline and operator selection is performed at the batch level, whereas performance-critical record operations are statically combined inside CPE kernels.For example, BGZF decompression, BAM parsing, and record-level statistics or filtering can be completed within one CPE launch.This avoids per-record runtime dispatch and unnecessary intermediate processing.Different pipelines can then be connected through MPE-side batch post-processing to construct complete operations such as BAM-to-BAM, BAM-to-SAM, and SAM-to-BAM conversion.In this way, SWBAM improves code reuse while preserving the optimized CPE execution path.

Based on this library, we further develop distributed implementations for more complex BAM operations.
Sorting and collation redistribute records among MPI ranks according to coordinate or QNAME information, respectively.Fixmate handles QNAME groups that may cross batch and rank boundaries.Duplicate marking uses a one-pass coordinate-streaming design with a sliding window, cross-rank boundary handling, and incremental output to control memory usage.These applications are further combined into an end-to-end deduplication workflow consisting of collation, fixmate, coordinate sorting, and duplicate marking.

The main contributions of this work are as follows:
\begin{itemize}
    \item We design SWBAM, a reusable BAM/SAM processing library for the heterogeneous Sunway many-core architecture. SWBAM provides four batch-based MPE-CPE pipelines together with common I/O, double buffering, distributed data access, and output support.
    \item We develop reusable and optimized CPE processing components for BGZF compression and decompression, BAM/SAM parsing and formatting, and record-level operations. SWBAM combines pipelines at batch boundaries and statically fuses record processing inside CPE kernels, reducing fine-grained scheduling and intermediate processing overhead.
    \item We implement distributed BAM applications on top of SWBAM, including sorting, collation, fixmate, and duplicate marking. These applications reuse the common library while introducing application-specific data redistribution, cross-rank state management, and a one-pass coordinate-streaming duplicate-marking algorithm.
    \item We integrate these applications into a complete distributed deduplication workflow and evaluate SWBAM at both the library and application levels on the Sunway platform.
\end{itemize}

\section{Methods}
\subsection{Overview}
% 总体介绍+库的介绍 -> app的介绍 -> overview图 √
As shown in Fig.~\ref{fig:swbam_overview}, SWBAM consists of a library and a set of applications that use its processing components.
The library provides common BAM/SAM I/O components for input partitioning and distributed output.
It also provides four batch-based pipelines for BAM reading, BAM writing, SAM reading, and SAM writing.
These pipelines use buffer reuse and double buffering to coordinate MPE--CPE execution.
MPE-side batch post-processing connects processing stages, while batch-level operators define task-specific operations.
Where appropriate, record-level operations are combined within CPE kernels.
CPE kernel optimizations further reduce allocation and data movement overhead in BGZF compression and decompression, BAM/SAM parsing and formatting, and record serialization.
These optimizations include codec reuse, reusable record buffers, and fused processing.

SWBAM applications reuse the library's processing components and implement algorithms for their specific data dependencies.
Streaming applications combine the relevant pipelines and operators for statistics, filtering, and BAM/SAM conversion.
Distributed applications reuse the BAM read and write pipelines, while application-specific algorithms and MPI communication handle record reordering and cross-rank state.
Sorting and collation redistribute records by coordinate and QNAME, respectively.
Fixmate processes QNAME groups across batch and rank boundaries, while duplicate marking maintains a coordinate-ordered candidate window and coordinates duplicate decisions across ranks.
These operations are combined into a four-stage deduplication workflow: collation, fixmate, coordinate sorting, and duplicate marking.

\subsection{SWBAM Library Design}
\subsubsection{BAM/SAM input and output}
%总结+分布式输入 → 分布式输出 √
SWBAM provides reusable BAM/SAM I/O components so that applications do not need to implement data access separately.
Applications can use the same processing pipelines with different I/O methods.
For BAM input, SWBAM divides BGZF blocks into contiguous ranges and assigns each range to an MPI rank.
The root rank scans the data region and builds an ordered index of block offsets and compressed sizes.
It reads compressed data into an 8-MiB buffer and examines successive BGZF headers in memory, reducing small file reads during block-boundary detection.
The root rank then broadcasts the index to all ranks.
The blocks are divided into contiguous ranges with approximately equal block counts.
During processing, each rank reads only its assigned blocks through POSIX or MPI-IO.
Within each contiguous batch, the BGZF blocks are read directly into separate destination buffers for CPE processing.
The POSIX path uses \texttt{preadv} to read a contiguous file region into a list of buffers.
The MPI-IO path uses a derived datatype to place each block in its corresponding destination buffer.
Both paths avoid an intermediate buffer and the subsequent copy of individual blocks.
For SAM input, SWBAM divides the text after the header into approximately equal byte ranges.
It adjusts partition boundaries to line ends so that each record remains intact within a single rank.
Each rank reads its assigned range through POSIX or MPI-IO.

SWBAM writes distributed output in two stages because each rank produces a different amount of data.
Each rank first appends its output body to a local store in memory or a temporary file.
In automatic mode, the store switches to a temporary file when an append would exceed the memory limit.
After processing, ranks exchange body sizes and use prefix sums to calculate file offsets in rank order.
Each offset is determined by the header size and the output sizes of all preceding ranks.
In MPI-IO mode, each rank reads its staged body through a fixed-size buffer and writes it to the assigned file region.
This avoids gathering complete output bodies on the root rank and limits memory use during final writing.
The BAM output consists of one header, the rank-local compressed bodies in rank order, and one BGZF EOF block.
The SAM output consists of one text header followed by the rank-local text bodies.
File-backed staging allows SWBAM to handle outputs larger than the available staging memory without keeping the entire output in memory.

\subsubsection{Batch-based MPE-CPE pipelines}
%总结+为什么以batch为核心 -> 介绍4条流水线 -> 介绍双缓冲优化 √
SWBAM provides four batch-based MPE--CPE pipelines for BAM reading, BAM writing, SAM reading, and SAM writing.
Batch-based execution reduces the kernel launch and synchronization overhead associated with per-record processing.
The MPE prepares input batches and manages task execution, while the CPEs perform the corresponding processing kernels.

The BAM read pipeline processes batches of compressed BGZF blocks.
The CPEs decompress the blocks and, when required, parse BAM records or perform application-specific operations.
The BAM write pipeline accepts uncompressed data blocks or batches of BAM records.
The CPEs compress the input blocks directly or serialize the records before compression.
Both pipelines produce or consume batches of BGZF blocks and support rank-local data processing.
The SAM read pipeline converts rank-local SAM text into batches of \texttt{bam1\_t} records.
The MPE divides the text into chunks aligned to record boundaries.
The CPEs first copy the text and count records, then parse the SAM fields in a separate kernel.
The SAM write pipeline converts batches of \texttt{bam1\_t} records into SAM text.
The CPEs format records into separate text buffers, and the MPE appends the results in record order.

SWBAM uses alternating buffers to overlap MPE-side work with CPE execution, as illustrated by the BAM read schedule in Fig.~\ref{fig:swbam_overview}.
For BAM reading, the MPE reads the next compressed batch while the CPEs process the current batch.
For BAM writing, the MPE writes the previous compressed batch while the CPEs compress the current batch.
Similar overlap is used in SAM processing, depending on the pipeline stages and data dependencies.
These strategies reduce idle time and reuse allocated buffers across batches without requiring multiple CPE kernels to execute concurrently within the same core group.

\subsubsection{Pipeline composition and operators}
% 总结+简单解释流水线和operators -> CPE记录级组合 -> 两个sdk组合示例 -> 介绍数据所有权与生命周期管理 √
SWBAM composes processing at two levels: record-level operations within CPE kernels and batch-level stages through MPE-side post-processing.
This design reuses common pipeline mechanisms while allowing applications to combine different operations without per-record dispatch overhead.
The pipeline runtimes manage batch buffers, launch and join CPE kernels, and invoke MPE-side hooks.
For each batch, an MPE-side operator provides the kernel entry and task-specific parameters, binds data buffers, validates the results, and performs batch-level post-processing.
These operators are invoked once per batch rather than once per record.

Within CPE kernels, SWBAM combines common BAM record traversal with task-specific operations, including record counting, flag statistics, basic statistics, filtering, and passthrough processing.
C++ templates determine the record operation when the kernel is compiled.
At runtime, the MPE selects among prebuilt kernels and passes task-specific options, such as filter parameters.
The record traversal invokes the selected operation directly, avoiding per-record virtual or function-pointer dispatch.

Batch-level composition connects pipelines through MPE-side post-processing after kernel completion and result validation.
For record counting, the BAM read pipeline parses records into reusable \texttt{bam1\_t} objects, and the MPE aggregates the per-block counts.
For BAM-to-BAM processing, the MPE groups retained records into BGZF packing plans and submits them to the BAM write pipeline for serialization and compression.
These plans reference existing records and do not copy record payloads or transfer ownership.
BAM-to-SAM and SAM-to-BAM processing similarly connect the corresponding read and write pipelines.

SWBAM also defines data ownership and lifetime across pipeline stages.
Pipeline-owned data remain valid only until their buffers are reused or released.
In BAM-to-BAM processing, parsed records remain in the read operator's storage until the downstream write call finishes consuming them.
The write call completes serialization and compression before returning, although compressed output may remain buffered for later writing.
Applications that retain data across batches manage its lifetime through their operators or algorithm-specific storage, copying data or directing kernel output to longer-lived storage when needed.

\subsubsection{CPE kernel optimizations} 
%总结 -> BAM相关优化 -> SAM相关优化 √
SWBAM optimizes CPE kernels to reduce repeated allocation, compression overhead, and intermediate data movement.
It reuses codec objects and working buffers, and combines related processing steps within a single kernel execution.

SWBAM reuses libdeflate compressor and decompressor objects across kernel launches.
Each CPE creates a decompressor on first use and reuses it for subsequent blocks.
Compressors are cached by compression level and recreated only when the required level changes.
For level-1 compression, SWBAM reduces match-search work by checking one hash-table candidate at each search position.
For sufficiently long matches, hash updates cover the first six interior positions and then use a two-byte stride.
These changes reduce candidate checks and hash-table updates while retaining valid DEFLATE and BGZF output.
For BAM input, SWBAM combines decompression, parsing, and record processing within one CPE kernel.
The decoded block is processed directly without a separate kernel launch or MPE-side processing stage between these operations.
Statistical kernels reuse a scratch \texttt{bam1\_t} record and its data buffer on each CPE.
BAM transform kernels instead store parsed records in preallocated arenas that are reused across batches, reducing per-record allocation.
For BAM output, SWBAM combines record serialization and BGZF compression within one CPE kernel.
Each CPE serializes the records specified by a packing plan into a reusable uncompressed BGZF payload buffer and compresses the payload directly.
This avoids an intermediate payload copy and a separate kernel launch between serialization and compression.
When serialized BAM payloads are provided directly, the kernel skips record serialization and compresses the input bytes.
Compressed output buffers are also reused across batches.

SWBAM also reuses buffers in SAM processing.
The fast SAM parser writes records into per-chunk arenas and caches recent reference-name lookups within each chunk.
Records that the fast parser cannot handle are processed by the general parser.
For SAM output, each CPE formats records directly into its batch text buffer instead of creating a separate string for each record.
The MPE reserves buffer capacity before formatting and retains enlarged buffers for subsequent batches.
These optimizations reduce repeated allocation and intermediate data handling in SAM parsing and formatting.

\subsection{Applications Built on SWBAM Library}
\subsubsection{Streaming BAM processing}
%总结+解释流式处理 -> 统计、过滤/重新、格式转换介绍 -> 与分布式算法的区别 √
SWBAM provides streaming BAM/SAM operations for statistics, filtering, rewriting, and format conversion.
These operations process records in input order without global record reordering, allowing each MPI rank to process its assigned input range independently.
For BAM input, record processing follows a separate BGZF scan that builds the block-span index.

Flag statistics use the BAM read pipeline and aggregate results at batch and rank levels.
CPEs update separate counter arrays, and the MPE-side flagstat operator merges these counters into rank-local totals after each batch.
An MPI sum reduction combines the rank-local totals on the root rank to produce the final report.
This operation does not generate an output BAM stream.
BAM filtering and rewriting connect the BAM read and write pipelines through the MPE-side transform operator.
The operator selects the filtering or passthrough CPE kernel according to the requested options.
After each batch, MPE post-processing groups references to retained records into packing plans that satisfy the BGZF payload-size limit.
The BAM write pipeline consumes these plans and appends the resulting compressed blocks to each rank's local output body.
Records retain their input order within each rank, and the final file places rank-local bodies in input-range order without coordinate- or QNAME-based sorting.
Format conversion connects the read pipeline for the input format to the write pipeline for the output format.
For BAM-to-SAM conversion, the MPE-side conversion operator forwards parsed BAM record references to the SAM write pipeline.
For SAM-to-BAM conversion, MPE post-processing builds packing plans from parsed SAM records and submits them to the BAM write pipeline.
Intermediate records remain valid until the downstream pipeline finishes consuming them, allowing the two pipelines to operate on batches without an additional record-level dispatch layer.

These streaming operations require little inter-rank communication after input partitioning because record processing remains local to each rank.
In contrast, the distributed algorithms described next require record redistribution or cross-rank state.

\subsubsection{Distributed BAM processing}
% 总结+分布式数据依赖 -> Sorting and collation -> Fixmate -> Duplicate marking
SWBAM implements distributed BAM operations that require global record reorganization or cross-record state.
Sorting establishes a global coordinate order, whereas collation groups records by QNAME.
Fixmate updates mate information for complete QNAME groups, and duplicate marking compares candidates across batches and MPI rank boundaries.
These applications reuse the common BAM read and write pipelines, while application-specific algorithms manage record redistribution, boundary handling, and cross-rank state.

\begin{figure*}[!t]
\centering
\includegraphics[width=\textwidth]{figs/swbam_distributed_reordering.pdf}
\caption{Distributed sorting and collation.
(a) Record redistribution and merging.
(b) Coordinate- and QNAME-based partitioning.
(c) In-memory and external-run processing.}
\label{fig:swbam-reordering}

Sorting establishes a global coordinate order through sampling, redistribution, and merging (Fig.~\ref{fig:swbam-reordering}).
CPEs extract coordinate keys and raw BAM records, while the MPE sorts local metadata and selects samples from the ordered records.
The root rank collects the samples, determines global splitters, and broadcasts them to define coordinate ranges for the MPI ranks.
Records are then exchanged according to these splitters.
Because the received segments are individually ordered, each rank performs a $k$-way merge rather than sorting all received records again.
The merged raw records are packed into BGZF payloads and compressed through the common BAM write pipeline.
Collation uses QNAME-based partitioning instead of constructing a global coordinate order.
CPEs extract QNAME hashes, record metadata, and raw BAM records.
Each hash is assigned to a bin, and each bin is mapped to an owner rank so that records with the same QNAME reach the same rank.
After local ordering, each rank retains self-owned records and exchanges the remaining records in bounded chunks.
The receiving rank merges the segments by bin, hash, and full QNAME, grouping records with the same QNAME together without imposing a global lexicographic QNAME order.
Within each group, records are ordered by READ1/READ2 flag bits and then by original input order.
Unlike the standard temporary-bin workflow of SAMtools~\cite{danecek2021samtools}, SWBAM supports both in-memory and external-memory collation.
Sorting also supports in-memory and external-memory execution.
In external mode, SWBAM generates sorted runs and performs bounded data exchange and streaming multi-way merging under the configured memory limit.
Figure~\ref{fig:swbam-reordering}(b) illustrates six coordinate ranges and 66 QNAME bins mapped to six ranks.
The merge fan-in $F$ limits the number of input segments processed per pass; additional passes are performed when necessary before final merging and compression (Fig.~\ref{fig:swbam-reordering}(c)).

Fixmate updates mate information for records with the same QNAME.
The BAM read pipeline supplies records from name-collated input, and the MPE groups consecutive records by QNAME.
Groups that extend across batch boundaries are retained until subsequent batches complete them.
The first and last rank-local groups are also deferred because they may extend across MPI rank boundaries.
Ranks exchange boundary QNAME information to identify group ownership and transfer the corresponding group fragments to their owner ranks.
For each complete group, a CPE planning kernel determines the required mate-field and tag updates and calculates the output size.
The MPE computes output offsets from the planned record lengths, and a second CPE kernel rewrites records into disjoint output regions.
The supported updates include mate coordinates, flags, template length, and the \texttt{MQ}, \texttt{MC}, and \texttt{ms} tags.
The rewritten records are then serialized and compressed through the common BAM write pipeline.
Boundary and interior output segments are combined in QNAME-group order.

\begin{figure}[!t]
\centering
\includegraphics[width=\columnwidth]{figs/swbam_markdup_single_column_v1.pdf}
\caption{Distributed duplicate marking.
(a) Boundary probing and cross-rank decisions.
(b) Candidate replacement and finalization in the sliding window.}

Duplicate marking compares candidates across MPI ranks while preserving input record order.
The BAM read pipeline supplies parsed records, and a dedicated CPE kernel extracts the duplicate keys and scores required for candidate comparison.
MPE-side logic assigns candidates to coordinate owners and maintains separate states for paired and single-read candidates.
MPI exchanges candidate metadata and routes decisions back to source ranks, while the original BAM records remain on their source ranks.
The sliding window retires candidate keys that can no longer match future records.
For a key coordinate $x$ on the current reference, an interior winner can be finalized as KEEP when
\[
x+L\leq p_r,
\]
where $p_r$ is the processed alignment-start coordinate on rank $r$, and $L$ is the configured maximum-read-length bound.
This condition relies on $L$ covering the possible displacement caused by clipping, including hard clipping.
Advancing to a later reference also expires keys from earlier references.
Figure~\ref{fig:swbam-markdup}(a) illustrates cross-rank decisions for candidates with the same unclipped $5'$ coordinate but different alignment starts.
Figure~\ref{fig:swbam-markdup}(b) shows candidate replacement and finalization for forward single-end reads.
Algorithm~\ref{alg:distributed_markdup} summarizes the processing and output workflow.

\begin{algorithm}[!t]
\caption{Distributed duplicate marking on rank $r$}
\label{alg:distributed_markdup}
\small
\hspace*{\algorithmicindent}\textbf{Input:} Rank-local coordinate-sorted BAM blocks; maximum read length $L$\\
\hspace*{\algorithmicindent}\textbf{Output:} Rank-local duplicate-marked BGZF body
\begin{algorithmic}[1]
\State $P_r \gets \Call{ProbeRankEnds}{r,32}$
\State $G \gets \Call{GatherRankStarts}{P_r}$
\State $H_r \gets \Call{BuildBoundaryPlan}{P_r,G,L}$
\Comment{Enable precomputation only when all rank boundaries are covered}
\State Initialize owner window $W_r$, pending blocks $Q_r$, and ordered output $O_r$
\State $T \gets \Call{AllReduceMax}{\text{number of local batches}}$
\For{$t=1,\ldots,T$}
    \State $(B_r,C_r,p_r) \gets \Call{DecodeAndExtractBatch}{t}$
    \State \Call{StartPreparedCompression}{}
    \State $C_r \gets \Call{CaptureAndApplyPlan}{B_r,C_r,Q_r,H_r}$
    \If{$H_r$ is disabled}
        \State $S \gets \Call{AllGatherProgressAndEOF}{p_r}$
    \EndIf
    \State $C_r^{\mathrm{owner}} \gets \Call{ExchangeByOwner}{C_r,G,Q_r}$
    \State $D_r \gets \Call{UpdateOwnerWindow}{W_r,C_r^{\mathrm{owner}},p_r,L,Q_r}$
    \If{$H_r$ is disabled}
        \State Add \Call{ReleaseSafeBoundaries}{$W_r,G,S,L$} to $D_r$
    \EndIf
    \State \Call{RouteAndApplyDecisions}{$D_r,Q_r$}
    \State \Call{FinishAndPrepareOutput}{$Q_r,O_r$}
\EndFor
\State Validate coordinate order across ranks
\State $D_r \gets \Call{FinalizeOwnerWinnersAsKeep}{W_r,Q_r}$
\State \Call{RouteAndApplyDecisions}{$D_r,Q_r$}
\State Verify that no source-record decision remains pending
\State Drain compression and seal $O_r$ in input-block and fragment order
\end{algorithmic}
\end{algorithm}

Boundary handling retains candidates until the required cross-rank comparisons are complete.
SWBAM probes up to 32 BGZF blocks at each end of a rank range and enables boundary precomputation only when all rank probes cover the required halo.
If coverage is insufficient, a conservative boundary window remains active until the relevant ranks advance beyond the boundary coordinate by $2L$ or exhaust their input.
In this fallback path, ranks exchange progress and EOF information so that boundary candidates are released only when no relevant remote candidate can remain.
During each processing round, candidates from the current batch are exchanged and processed before safe boundary release.
Ranks that finish early continue participating in collective rounds with empty batches.
Records awaiting remote decisions remain pending after local EOF until their owners' decisions arrive.
Only blocks with fully resolved duplicate decisions enter compression.
Compression may complete out of order, but compressed fragments are indexed by input-block and within-block position to preserve the final logical order.
Decoded buffers remain valid while active compression uses them; unresolved blocks may be staged temporarily under cache pressure.
The common library manages batch execution and compression, while the application maintains the sliding window, boundary state, MPI decisions, pending blocks, and output-order metadata.

\subsubsection{Deduplication workflow}
%总结端到端去重流程 -> 解释四个阶段的执行顺序 -> 介绍中间文件与参数管理 √
SWBAM combines collation, fixmate, coordinate sorting, and duplicate marking into an end-to-end deduplication workflow.
The stages run in this order because fixmate requires records with the same QNAME to be grouped together, while duplicate marking requires updated mate information and coordinate-sorted input.
The workflow first groups records by QNAME using collation, then runs fixmate with mate-score calculation enabled, sorts the updated records by genomic coordinate, and finally marks duplicates.
Each stage uses the corresponding distributed SWBAM application and the common BAM input and output interfaces.
The output of each stage is written to an intermediate BAM file and passed to the next stage.
The workflow produces collated, fixmate-updated, and coordinate-sorted intermediate files before generating the final duplicate-marked BAM file.
Intermediate files can be removed automatically after use or retained for debugging and validation.
The memory limit and compression settings are propagated to the relevant stages, while sorting and collation can use their external-memory implementations when needed.

The library benchmarks measure BAM reading and writing and examine MPE-CPE optimizations.
