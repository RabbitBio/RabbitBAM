# D2 markdup 延后转存诊断

更新：2026-10-13 17:25。单次诊断，不作为正式性能样本。

## 结论

rank 1 的高频转存主要来自短时窗口积压形成后，输出调度不能追赶输入。
不是边界预处理回退，也不是同一批反复转存；不能将 81% 解释为 81% 的
输入批次在整个处理过程中都需要等待判重。

|---|---:|
| 处理批数 | 5165 |
| 转存次数 / 不同转存批数 | 4191 / 4191 |
| 重复转存次数 | 0 |
| 读回次数 | 4191 |
| 转存时已就绪块 | 266237 |
| 转存时含未决记录块 | 1958 |
| 已就绪块占转存块比例 | 99.2699% |
| 累计写入 / 读回 bytes | 17460461230 / 17460461230 |
| 转存路径 / 读回路径耗时 | 7.627252 / 7.519205 s |

转存次数除以读入批数为 81.1423%，是累计事件比例，不是瞬时缓存占用。
本次恰好每个转存批只写入一次，随后读回一次；其余五个 rank 转存为零。
路径计时包含转存分配/写入/释放和读回分配/读取/释放，合计 15.146457 s。
不能直接从端到端时间减去该值宣称优化收益，修改调度后还需实测。

## 调度原因

`MdOnePassPrepareOutput` 每次最多准备 64 个输出 BGZF 块，
`MdPostProcessOnePassBatch` 每读取一批只完成一次旧输出并准备一次新输出。
正常一批读入也是 64 个块，因此窗口恢复后“进 64、出 64”，已有积压不下降。
直到输入结束后，`MdDrainOnePassOutput` 才循环排空。

约 4643 个待完成输入块的缓冲槽需要 290.19 MiB，超过 256 MiB 缓存门槛。
`MdOnePassSpillPending` 超限时降至约半门槛；此后新批进入、旧批读回，
队列仍维持相同深度，导致在大部分后续扫描中持续转存已就绪数据。

建议先在缓存压力下增加有界的就绪前缀追赶：真正未决时继续读入，
前缀已就绪且队列过大时额外压缩几批，降到低水位再恢复现有重叠调度。
这样维持原有块序和快速路径，不必先为本次问题增加乱序输出片段管理。
若确实出现长期未决前缀且后方就绪块大量积压，再考虑独立 BGZF 暂存机制。
