# Level-1 压缩搜索优化的输出体积对照

## 目的与口径

测量论文中 `X\% on average (X\%--X\% across D1--D3)`：在相同 BAM 数据、记录顺序、BGZF 载荷和块边界下，仅改变 CPE level-1 压缩搜索策略。

- 原始策略：项目内 libdeflate 的 `deflate_compress_fastest`，恢复 level-1 默认 `nice_match_length=32`，关闭 single-probe。
- 优化策略：正式 SDK 使用的 single-probe + head6/stride2，`nice_match_length=4`，stride2 的匹配长度阈值为 5。
- 每个数据集的增幅：`100 × (优化版完整 BAM 字节数 / 原始版完整 BAM 字节数 − 1)`。
- 平均值：D1、D2、D3 三个增幅的算术平均；范围：三者的最小值与最大值。
- 本实验不测性能，不将旧 SWBAM 与 RabbitBAM 的整个输出大小差异当作压缩器消融结果。

## 实验方法

1. POSIX 流式读取完整输入，复用正式 SDK 的无过滤 `RunBamTransformPipeline`，生成并保留 rank-local BGZF body。
2. 解压每个实际输出块，使用同一份未压缩载荷分别调用原始和优化后的 CPE 压缩器；不改变打包方式。
3. 优化版重压缩块必须与第 1 步的正式 SDK 输出逐字节相同。
4. 两种压缩结果均通过独立的 MPE libdeflate 解压，检查载荷、BSIZE、ISIZE 和 CRC；覆盖所有输出块。
5. 分别累计 body 字节数，再加上相同的 SDK BAM header 和一个 28-byte EOF，得到完整 BAM 大小。无需将两套大 BAM 都写到磁盘。

使用一个节点、6 个 MPI ranks、每 rank 64 个 CPE。输入不全量加载到每个 rank；仅保留本 rank 的 SDK 输出 body。三个数据集分配到三个节点并行执行。

```tex
2.82\% on average (2.50\%--2.99\% across D1--D3)
```

三份完整输入共 708,251,833 条记录、3,405,238 个输出 BGZF 块。所有块的原始/优化压缩结果均通过独立解压和 CRC 校验；优化结果均与正式 SDK 输出逐字节相同。小样本只用于工具验收，不参与平均值计算。

这组比例适用于上述同输入、同 BGZF 打包的 BAM 重写对照，不代表全部应用输出的平均增幅；过滤、排序和其他记录变换可能改变压缩内容及布局。

Smoke：112,906 records、596 个输出块，原始 16,068,214 bytes，优化 16,294,106 bytes，增幅 1.405831413%；两种策略均通过全部解压/CRC 校验，优化输出与正式 SDK 输出逐字节相同。

## 构建与运行

```bash
cmake -S . -B build_bounded_io/validation_local_digest_20261112 \
  -DBUILD_SWBAM_APP=OFF -DBUILD_SWBAM_EXAMPLES=OFF -DBUILD_SWBAM_TOOLS=ON
cmake --build build_bounded_io/validation_local_digest_20261112 \
  --target swbam-codec-ratio-probe -j8

# 在 SWLS 的实验目录提交；各数据集的完整路径和命令见 *.job.json。
bsub -node "$NODE" -N 1 -np 6 -health 1 \
  -cgsp 64 -share_size 14000 -cache_size 32 \
  -a mpi -b -K -q q_swtofs -timelimit 02:00:00 \
  -J "codec_ratio_$DATASET" -o "logs/$DATASET.log" \
  ./bin/swbam-codec-ratio-probe "$INPUT" "$EXPECTED_RECORDS"
```
