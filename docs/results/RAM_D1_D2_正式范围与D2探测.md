# RAM D1/D2 正式范围与 D2 探测

更新：2026-10-12。此文登记新版 RAM 端到端补测，不替代历史核心时间表。
本轮只测试 D1/D2；D3 作为历史/探索记录保留。

## 正式范围

| 类别 | 命令 | 计算资源 | 重复 |
|---|---|---|---|
| SDK 只读 | `swbam-sdk-optimized-count`，CPE 构建 `bam1_t` 后计数 | 建议 1/2/4/6/12 ranks，各 rank 一个 64 CPE 核组 | 每点三次 |
| SDK 读写 | `swbam-sdk-optimized-bam2bam`，完整 level 1 BAM | 同上 | 每点三次 |
| 普通 app | flagstat、SAM->BAM、BAM->SAM、MAPQ>=30 过滤 | 六节点六 ranks、六活跃核组 | 每项三次 |
| 复杂 app | collate `-n 66`、sort、fixmate `-m`、markdup `--stream` | 同上；D1/D2 内排 | 每项三次 |
| 普通串联 | collate -> fixmate -> sort -> markdup | 四条独立 MPI 命令 | 三轮，逐轮区间合计再取中位数 |

SDK 简单曲线的五个资源点已用于 D1 正式矩阵；D2 计划采用同一组点，先通过容量验证。
`-m` 是各算法工作区预算，不是 RAM 存储池预算。当前不启动 app 扩展性、
消融、大规模外排性能或 dedup 包装命令的 RAM 矩阵。stats/io-check 仅用于验证。
若按上述五点实施，共 60 个 SDK、48 个独立 app、24 个四步阶段性能命令，
另计输出准备和正确性检查。2026-10-12 已单独启动其中的 D1 半矩阵：
66 条性能命令加 8 条完整输出复读，见 [D1 正式测试](RAM_D1_正式性能测试.md)。
D2 正式矩阵尚未启动；2026-10-12 已部署“补齐容量关卡 -> 等待 D1 完成 ->
D2 正式矩阵”的条件驱动，见 [D2 关卡与矩阵](RAM_D2_容量关卡与正式矩阵.md)。

主成绩为各 rank `MPI_Init` 前至 `MPI_Finalize` 后真实耗时的最大值。
MPI 前池预触碰、预加载、就绪同步，以及 Finalize 后保存均在区间外；正常
解析、扫描、通信、工作区管理、RAM I/O、清理均在区间内。核心时间仅作诊断。
四步前三阶段必须保存，下一条重新预加载，不用独立阶段中位数相加代替完整三轮。

以上性能项都是单次探测，不是正式三次中位数。独立写 app 使用 `--no-dump`，
表中的输出大小为实际 RAM 文件布局；不能将运行自检称为全量跨工具字段验证。

sort 已正常进入 MPI、解析了 2,017,608 个 BGZF 数据块，选择 memory mode。
输入每 rank 约 8.962 GB，预触碰池为 24 GiB，算法 `-m 48G`。
全部 rank 在 `MpiSortExchangeBuckets` 的发送缓冲分配报 `std::bad_alloc`，
每 rank 要打包约 60.85M 条记录及 21.519 GB raw bytes。最后均输出 `status=1`。
这不是排队、磁盘 quota 或仅 RAM 文件页耗尽；失败处是算法工作区的普通内存分配。
24 GiB 池整体占用与 raw 容量增长、metadata、索引和 send buffers 同时叠加，
不能按日志的 9.03 GB RAM 已用页或选路公式估计整个堆峰值。
内排 `-m` 的检查也不代表发送阶段所有活跃分配都被严格限制到 48 GiB。

后续应先检查减小 sort 的 RAM 池预算是否仍能容纳完整输入/输出，再进行单项探测；
若仍不足，再定位算法分配峰值。当前未修改算法、未将 sort 改成外排，
也没有把失败轮重新记为成功。本次优先启动容量余量较大的 D1 正式矩阵。

RAM 池会按整个 capacity 分配并预触碰，不能把日志的已用页 peak 当作全部内存
占用。例如 sort 使用 24G 池加 48G 工作区预算，仍须保留正常控制与额外分配余量。
collate/sort 必须确认 `selected mode=memory`；这次不探测外排性能。

除 SDK 输出外，本次复用已有完整 SAM、collate、fixmate 和坐标排序输入，
每条 app 独立各跑一次。它验证容量和运行自检，不是新版完整四步串联，
也不能用无 dump 的算法计数汇总冒充全量输出内容验证。
正式串联必须由新版每轮从初始 BAM 重新生成全部中间文件。
