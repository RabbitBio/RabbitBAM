# Markdup 数据集差异与缓冲诊断

## 问题与结论边界

解释最新正式结果中 D1/D2/D3 的 3.00x / 2.30x / 1.43x 时间比。正式时间使用 2026-11-09 优化版的三次中位数；SWBAM 为六节点六活跃核组的 RAM processing，SAMtools 为 a4 实盘 wall，仍不是同机同存储比较。本页不覆盖论文或正式表。

现有日志支持：**D2 的问题不是主循环候选传输；D3 有额外边界状态维护；两者都存在比 D1 更重、更不均衡的 MPE 窗口工作。** 暂存机制的独立影响通过下面的诊断对照检查，不根据累计字节量直接推断耗时。

### 1. D2：本地窗口与负载不均衡

D1/D2 都完成边界预处理，主循环候选和判定 payload 均为零。因此 D2 的下降不能归因于跨 rank 候选传输。

窗口的 key 哈希、赢家比较、跨批 carry/QNAME 维护和记录状态更新主要在 MPE 完成，不直接获得每 rank 64 CPE 的块级并行加速。相同块数分区并不保证这些工作均衡：D2 各 rank 的累计 `group` 时间相差约 1.70 倍，D1 约 1.03 倍。

`MdPostProcessOnePassBatch` 在窗口前后仍有全局状态 collective；无候选 payload 不等于无同步。慢 rank 会使其他 rank 等待。但现有计时未把所有状态 collective 单独统计，不能把全部 `unaccounted` 直接解释为 MPI 等待，也不能给出精确等待占比。

D2 每记录的压缩输出比 D1 大约 63%，BGZF 块数也更多，因此打包、编解码与内存流量的工作量并不按记录数等比例增长。这是额外因素，不等于“读长解释了全部差异”。

### 2. D3：密集边界与更重的状态维护

固定首尾 32+32 块的探测不能完成全部覆盖，当前版本是 partial，而不是完全不做预处理。已知 DUP 可先处理，未决赢家仍由主循环保守维护。

主循环保留 541,474 条普通远程候选，另有 marker。边界状态处理集中在少数 rank，`group` 的最大/最小约 2.70 倍，pending 峰值明显超过 D1。它说明空间分布与状态存活时间改变了工作量，不能仅按人/鼠物种差异作解释。

正式第 1 次日志的 `candidate_mpi` 最大值约 D1 0.0049 s、D2 0.0117 s、D3 0.1123 s。该指标仅覆盖指定候选 payload 交换区段，不覆盖所有 MPI setup、判定交换、状态 collective 或等待；不能用它宣称总通信成本为零。现有证据不支持把几十秒的差距主要归因于 88.65 MB 候选的网络带宽。

### 3. 必须区分两类中间写出

- **原始块暂存**：未决记录使 decoded block 滞留，超过缓存阈值后保存 raw payload，判定后重载。D2 只有 0.127 GB，每方向，不是 13.766 GB。
- **压缩块重排暂存**：后续就绪块可以先压缩；压缩顺序首次偏离输入顺序后，`OrderedBody` 保存带 block key 的压缩段，最后按输入顺序读取。D2/D3 的临时字节主要来自此处。一次较早的乱序就可能使后面很大一段输出进入该机制，不能把全部字节视为异常溢出。

两类均通过 RAM backend 模拟，**不是真正写物理磁盘**。累计字节量既不是同时驻留量，也不是耗时。放大 raw 缓冲不必然关闭压缩段重排；保留所有 decoded blocks 也可能增加内存扫描和延迟压缩，不能预设一定更快。

## 额外对照实验

仅诊断，不替换正式三次成绩，不修改生产代码或默认程序。

- D2/D3 各一次默认缓存、一次放大缓存，共 4 个有效样本目标。
- 同一 markdup 代码、`--stream -l 300 -m 8G --compress-level 1`，六节点六活跃核组、24 GiB/rank RAM 存储池、完整 RAM 输出。
- 两边均开启既有 `SWBAM_MARKDUP_PENDING_DIAG=1`。`--no-dump` 只省物理保存，不省 RAM 输出。
- 默认程序为正式 `d7c8db1c...`；实验程序只将私有 benchmark-support 的 `CacheMemoryLimit()` 上限从 256 MiB 增至 2 GiB，`work_memory / 16` 下限/规则保留。它同时放大 ordered-body metadata 预算，但不去掉压缩段重排。
- 比较 processing、raw spill/reload 字节与耗时、compressed temp 字节、跟踪内存、候选通信和完整输出大小；检查六 rank 状态、记录数和 DUP 总数。不宣称全量逐记录输出等价。
- 新构建位于 `build_bounded_io/verification/markdup_buffer_probe_20261109/build/`；源码快照和私有 support 修改独立保存，默认源码不变。
- 驱动：`tools/markdup_buffer_probe.py`。日志、实际提交命令和二进制指纹：`build_bounded_io/verification/markdup_buffer_probe_20261109_run1/`。
- 首次提交在默认 base 工作目录被拒绝，未创建作业；之后修正为实验目录。固定节点的三个 PEND 作业 `9101910/9101911/9101912` 报 `RMS_NODE_UNAVAIL_ERROR`，确认无 session/log、未启动后取消，保留原因记录，改为调度器分配节点。
- 有效作业：D2 默认 `9101949`、D2 大缓存 `9101950`、D3 默认 `9101951`、D3 大缓存 `9101913`。后者使用此前可用的 `43316–43321`；其他实际节点以调度日志为准。不同节点、单次诊断和诊断打印均需保留限制，不能代替交错三次正式消融。

四个有效作业于 **11:35** 全部完成，无本轮活动作业。单位为秒、十进制 MB/GB。

| D2 | 138.149338 | 137.687259 | -0.33% | 269.418 | 316.112 |
| D3 | 92.506219 | 90.907103 | -1.73% | 282.563 | 1,362.276 |

| 数据 | 默认 raw spill 批数 | 大缓存 raw spill 批数 | 消除的 raw 暂存 / GB，每方向 | 保留的压缩块暂存 / GB，每方向 |
| --- | ---: | ---: | ---: | ---: |
| D2 | 33 | 0 | 0.127409 | 13.638815 |
| D3 | 594 | 0 | 2.389567 | 14.067890 |

默认版本 raw spill/reload 的单 rank 最大计时分别为：D2 **0.060 / 0.063 s**，D3 **0.484 / 0.526 s**。这是各操作计时的 rank 最大值，不是可相加的全局关键路径占比。大缓存两项均为零。

大缓存没有降低窗口判重负担：D3 的最大 `group` 时间仍约 40.7 s。跟踪总工作集峰值由 538.732 MB 升至 1,612.059 MB；pending 峰值约为原来的 4.82 倍，不能表述为整个进程 RSS 增加 4.82 倍。两边的 RAM 存储池容量均为 24 GiB/rank。

**本轮没有观察到取消 raw spill 带来大幅提速，不建议仅为这点收益放弃默认有界策略。** D2 的 0.33% 差异尤其不能在单次、不同节点条件下解释成确定收益。D3 约 1.73% 是探测结果，不是新正式中位数，不替换 92.502027 s。

注意 D2 本轮默认/大缓存都慢于正式 131.161046 s 中位数约 5%，执行节点与诊断开关也不同，未隔离各自贡献。不能拿大缓存 137.687259 s 与正式旧值直接比较以证明缓存回退，也不能声称本次同时消融了所有中间写出。

压缩块暂存的字节量在对照两边**完全相同**。因此本实验只评价原始块 spill 和相关压力调度变化，尚未测得取消 `OrderedBody` 压缩暂存的独立收益。后者需要另一套保证输入顺序、完整输出且记录内存峰值的对照，不能依据本轮结果一并判为无成本。

### 验收与保留

四个样本六 rank 状态、预期记录数、DUP 总数和完整 RAM 输出均通过；两版本逐 rank 的 examined/excluded、pair/single/owner candidates、QNAME 字节、pair/single duplicates、marked/cleared/removed、BGZF 数以及全部预处理/主循环通信统计一致，最终压缩输出大小一致。未物理保存和逐记录复读，不把计数/大小一致扩大成全量输出等价。

原始证据位于上述 run1 目录的 `jobs.json`、`binaries.sha256`、`inputs.tsv`、`results.json`、`logs/` 和 `state.json`。`evidence_summary.json` 保留日志 SHA-256、逐 rank 对照验收及 11:20 时观察到的实际节点；完成后调度器较快清除历史，部分 `bjobs -l` 已返回 invalid job id，不据此否定完整应用日志。实验程序 SHA-256 为 `3f0a8f2f770fce16b0f963216b59c0c38e634ca3b56bae048e0176cb879e0bc6`；正式程序指纹与正式结果均保持不变。

## 对论文的解释建议

可以说明 markdup 的扩展收益具有工作负载敏感性：批量 CPE 编解码得到并行加速，但 MPE 侧的窗口维护、跨批状态与 rank 间工作量不均衡限制了整体收益；D3 的部分边界覆盖又增加了状态维护和同步依赖。不要写成“数据越大加速越低”“都是网络通信导致”或“删临时文件就会达到 D1 的加速比”。

阶段时间存在嵌套和重叠，表中各阶段最大值不能直接相加作为关键路径。本文区分日志确认的事实、源代码支持的机制解释以及尚未消融的成本，不给全部暂存机制分配未经测量的耗时比例。
